【v5 关键改动 —— 镜像现在是"自给自足"的】
飞牛官方镜像自带的 U-Boot 是给 Firefly-RK3399 编的（控制设备树
firefly,firefly-rk3399），在 AM40 的板级初始化阶段就挂了 —— 现象正是
【网口灯完全不亮、什么都没起来】，这就是 v1 起不来的根因。
本镜像已把那套 U-Boot 替换成 AM40 上【已验证可用】的 Armbian U-Boot
（从本机 eMMC 的 0~16MB 裸区提取，md5 43d1cb8be212412dc8b427ab254307ee）。

=> 刷 SD 能从 SD 启动，刷 eMMC 能从 eMMC 启动，互不依赖。

--------------------------------------------------------------------------------
一、⭐ MPP 硬件编解码：已验证可用（默认开启）
--------------------------------------------------------------------------------
rk3399-smart-am40-mpp.dtb = 原版 DTB + mpp_srv + VDPU2/VEPU2 节点。
启动后：
    mpp_service mpp-srv: probe success
    mpp_vdpu2 ff650400.vdpu: probing finish     ← H.264/VP8 硬解
    mpp_vepu2 ff650000.vepu: probing finish     ← H.264 硬编
    /dev/mpp_service 出现
实测（/usr/bin/ffmpeg 自带 rkmpp）：
    h264_rkmpp 编 720p x90  -> CBR 3.8Mbps，输出 1.41MB   ✔
    h264_rkmpp 编 1080p x60 -> 输出 1.42MB                 ✔
    h264_rkmpp 解 720p/1080p -> 60/90 帧全解，speed 6~7x    ✔
HEVC/4K 解码仍走 mainline 的 V4L2 rkvdec（/dev/video0）。
一句话：不用换内核就拿到了 H.264 硬解 + 硬编。

  * 权限：/dev/mpp_service 默认 0600 root。重刷后执行一次（规则就在本分区）：
        sudo cp /boot/99-am40-mpp.rules /etc/udev/rules.d/
        sudo udevadm control --reload-rules && sudo udevadm trigger --action=change
        sudo usermod -aG video $USER
  * 已知副作用：飞牛自带的 mediasrv 发现 MPP 可用后会 SIGSEGV 无限重启
    （日志 "mpp_platform: client 9 driver is not ready!" -> signal=SEGV）。
    它自己的 bug。二选一：
        sudo systemctl mask mediasrv          # 不要飞牛自带媒体服务
        fdtfile 改回 rk3399-smart-am40.dtb    # 要 mediasrv，放弃 MPP
    Jellyfin 用自己的 ffmpeg 走 /dev/mpp_service，不受影响。

三、刷到哪里？两条互斥的路线
--------------------------------------------------------------------------------
路线 A：SD 当系统盘，eMMC 当存储空间
    就按现在这样用 SD 启动；在飞牛 UI 里把 eMMC 格式化成存储空间。
    因为本镜像已自带启动链，eMMC 怎么格式化都不影响开机。

路线 B：eMMC 当系统盘（不需要 maskrom）
    sudo dd if=<本镜像> of=/dev/mmcblk0 bs=4M conv=fsync status=progress
    ⚠ 刷完请【把 SD 拔掉或清掉】：两份镜像的文件系统 UUID 与 GPT PARTUUID
      完全相同，同时插着会撞车（root=PARTUUID=... 可能挂到另一块盘上）。
    ⚠ eMMC 上原来的旧飞牛会被覆盖。
    首次启动 resize-rootfs 会自动把 rootfs 扩到 eMMC 的 99%（约 29GB）。

mediasrv 崩溃根因（2026-09-16 实测定位）
--------------------------------------------------------------------------------
现象：journalctl -u mediasrv 每 5 秒一轮
      Started -> mpp[...]: mpp_platform: client 9 driver is not ready! -> status=11/SEGV
根因：mediasrv 启动时向 MPP 要 HEVC 那一路，本 DTB 只让 MPP 绑定 H.264 两路
      (mpp_vdpu2->ff650400.vdpu 解 / mpp_vepu2->ff650000.vepu 编)，
      它不检查返回值 -> 空指针 -> SIGSEGV。ffmpeg 遇同样错误会优雅返回，是 mediasrv 自己的 bug。
      RK3399 的 HEVC/VP9/4K 解码器 ff660000.video-codec 归 mainline V4L2 驱动(/dev/video0 "rkvdec")，
      不是 MPP 客户端；且 RK3399 没有 HEVC 硬编。
处理：sudo systemctl mask mediasrv          # 止血（Jellyfin 不受影响）
      或 fdtfile 改回 rk3399-smart-am40.dtb  # 保 mediasrv，弃 MPP
提示：HEVC 硬解可走 fnOS ffmpeg 的 hevc_v4l2m2m(/dev/video0)；H.264 用 h264_rkmpp。

【更正 2026-09-16 22:45】主线 rkvdec 其实是能用的，之前写错了
--------------------------------------------------------------------------------
/dev/video0 = rkvdec (rockchip-vdec.ko, Boris Brezillon/Collabora, of:rockchip,rk3399-vdec)
接口是 stateless / V4L2 Request API，实测 ioctl 枚举：
  OUTPUT_MPLANE : S264="H.264 Parsed Slice Data"  VP9F="VP9 Frame"
  CAPTURE_MPLANE: NV12   caps: VIDEO_M2M_MPLANE|EXT_PIX_FORMAT|STREAMING
=> 所以 *_v4l2m2m（stateful 包装）报 "Could not find a valid device" 是正常的；
   正确用法是 -hwaccel v4l2request，实测真硬件：
     H.264 软解 utime 0.950s -> v4l2request 0.374s  ✅
     VP9   软解 utime 1.503s -> v4l2request 0.309s  ✅
     HEVC  v4l2request 2.020s ≈ 软解（驱动不暴露 HEVC）✗
支持：H.264(8bit) + VP9(profile0/8bit) 解码，4K@60；不暴露 HEVC/10bit；只解不编
hantro_vpu 这个内核没编 -> 主线给不了 H.264 硬编、也没有 MPEG/VC-1/VP8/H.263 解码
混栈不行：v4l2request 的帧喂 h264_rkmpp 失败（hwmap rc=139 / hwdownload+hwupload rc=218）
=> 转码仍是「软解 + MPP 硬编」或全 MPP(H.264)；VP9 硬解用于纯解码/缩略图场景

【2026-09-16 22:40】官方 6.1 BSP 怎么绑 RK3399 的 VPU / 为什么我们不能全走 MPP
--------------------------------------------------------------------------------
官方 kernel-develop-6.1 BSP（= 和飞牛 MPP 同源的 nyanmisaka 树，源码在 kernel/kernel-develop-6.1.zip）
的 rk3399.dtsi 里，四个 MPP 节点是：
  mpp-srv            compatible = "rockchip,mpp-service"  taskqueue-count=2 resetgroup-count=2
  vepu@ff650000      compatible = "rockchip,vpu-encoder-v2"  srv=&mpp_srv taskqueue=0 resetgroup=0
  vdpu@ff650400      compatible = "rockchip,vpu-decoder-v2"  srv=&mpp_srv taskqueue=0 resetgroup=0
  rkvdec@ff660000    compatible = "rockchip,rkv-decoder-rk3399"  srv=&mpp_srv taskqueue=1 resetgroup=1
  （同时 mainline 的 vdec@ff660000="rockchip,rk3399-vdec" 和 vpu@ff650000="rockchip,rk3399-vpu" 都 status="disabled"）
=> 我手搓的 mpp DTB 与官方完全一致，DTB 层面没问题。

差别在编译开关：mpp_rkvdec.c 里 rk3399 那条匹配被 #ifdef CONFIG_CPU_RK3399 包着，
飞牛的内核/模块没有开这个符号。

关键：MPP 其实是可加载模块
  /lib/modules/6.18.18.c1090-trim/updates/trim/rk_vcodec/rk_vcodec.ko
  （所以 /boot/config-* 里没有任何 MPP 符号、kernel/drivers/.../mpp/ 是空的）
  该 ko 里的 compatible 只有 rkv-decoder-rk3528/rk3562/rk3568/rk3576 + rkv-decoder-v1/v2/v2-ccu…
  没有 rk3399 -> 编译时 CONFIG_CPU_RK3399 未开

=> 想"全部走 MPP"：不必重编内核，只要用同一份 MPP 源码开 CONFIG_CPU_RK3399 重编
   rk_vcodec.ko（板子上已有 gcc/make + 内核头文件 + Module.symvers），替换后配满编 DTB 即可。
   回滚：把备份的 rk_vcodec.ko 拷回（模块坏了不影响开机）；MPP 解码卡死则断电 + fnEnv 换回旧 DTB。

2026-09-16 23:05 ★ mediasrv 崩溃已修复（根因 = DTB 里 RGA 节点的 compatible）
================================================================================
现象：mediasrv 起来 3 秒就 status=11/SEGV，日志只到
      "[info] cache dir ... invalid"，之前从来没打印过 "gpu in working"。
      崩溃栈是 librga.so.2.1.0 里的 DABT level 0 translation fault。

根因链（一句话：DTB 的 rga 节点没有任何驱动认领 -> 没 /dev/rga -> librga 一调就崩）：
  1. DTB 里 rga@ff680000 compatible = "rockchip,rk3399-rga"（上游 mainline 的写法）；
  2. fnOS 内核 CONFIG_VIDEO_ROCKCHIP_RGA is not set（没有 mainline 版 RGA 驱动）；
  3. fnOS 只发 vendor 版 rga3.ko，strings 出来的 of_match 只有：
     rockchip,rga2 / rockchip,rga2_core0 / rockchip,rga3 / rockchip,rga3_core0 / rockchip,rga3_core1
     —— 没有 rk3399-rga，modinfo -F alias 也是空的（连 autoload alias 都没有）；
  4. 模块 by name 能 insmod，但 rga2_driver/rga3_driver 谁都匹配不上这个节点
     -> rga_drvdata->num_of_scheduler = 0
     -> rga_drv.c 的 rga_iommu_bind() 里 main_iommu_index / main_mmu_index / another_index 全是 -1
     -> pr_err("%s, binding map scheduler failed!") 然后 return -EFAULT
     -> dmesg: rga_iommu: rga_iommu_bind, binding map scheduler failed!
              rga: rga iommu bind failed!
     -> modprobe: ERROR: could not insert 'rga3': Bad address
  5. 没有 /dev/rga -> mediasrv 里 librga 空指针解引用 -> SEGV。

为什么"官方也是这么写的"：
  kernel-develop-6.1/arch/arm64/boot/dts/rockchip/rk3399-linux.dtsi 的 rga 节点就是
      compatible = "rockchip,rga2";  clock-names = "aclk_rga","hclk_rga","clk_rga";
  而且 arch/arm64/configs/rockchip_linux_defconfig 里 CONFIG_ROCKCHIP_MULTI_RGA=y（就是编出 rga3.ko 那个）。
  4.4 的 rk3399-firefly-android.dts 同样写 "rockchip,rga2" 并带 dev_mode = <1>。
  => 是 fnOS/AM40 这份 DTB 从 mainline 抄了 "rockchip,rk3399-rga"，跟它自己发的模块对不上。
  （和 MPP 那个坑一模一样：DTB 与模块不是一套。）

修法（只改 DTB 一个属性，板子上 dtc/fdtput 都有，不用重编内核、不用重刷）：
  sudo cp /boot/dtb/rockchip/rk3399-smart-am40-mpp-full.dtb \
          /boot/dtb/rockchip/rk3399-smart-am40-mpp-rga.dtb
  sudo fdtput -t s /boot/dtb/rockchip/rk3399-smart-am40-mpp-rga.dtb /rga@ff680000 compatible "rockchip,rga2"
  sudo sed -i 's#fdtfile=.*#fdtfile=rockchip/rk3399-smart-am40-mpp-rga.dtb#' /boot/fnEnv.txt
  sudo reboot
  # 重启后开机就自动加载 rga3，然后
  sudo systemctl enable --now mediasrv

修完的验证（dmesg）：
  rga2 ff680000.rga: probe successfully, irq = 83, hw_version:3.2.18218
  rga_iommu: IOMMU binding successfully, default mapping core[0x4]
  rga: Module initialized. v1.3.4
  # hw_version 3.2.18218 落到驱动兜底档 rga2e_data，mmu = RGA_MMU（RGA2 自带页表，不需要 iommus）

顺便验证 RGA 真能算：

2026-09-16 23:40 ★ AV1 视频也能播了（mediasrv 兼容垫片）
================================================================================
RGA 修好之后 mediasrv 能起来了，但播 AV1 还是报错。用 -l debug 抓到真实链路，
发现是两个"RK3399 硬件能力"问题叠在一起，都不是飞牛的 bug：

问题 1：RK3399 没有 AV1/VP8 硬解，mediasrv 却硬要开 av1_rkmpp
  [debug] codec_id 225, Rockchip MPP (Media Process Platform) AV1 decoder
  [debug] hw devices decoder=rkmpp, filter=rkmpp
  [error] avcodec_open2 for video decoder error / errno -542398533 (AVERROR_EXTERNAL)
  journalctl -u mediasrv 原话：
    [av1_rkmpp] Failed to init MPP context: -1
    mpp: unable to create dec av1 for soc rk3399 unsupported
  => MPP 自己知道 rk3399 不支持 AV1，但 mediasrv 是用 av_codec_iterate() 遍历全部解码器、
     按名字带 rkmpp 后缀来挑的，只看到"有个 av1_rkmpp"就以为能用。
     注意：mediasrv 二进制里连 "av1_rkmpp" 字符串都没有（名字运行时拼的），
     也不用 avcodec_find_decoder_by_name()，所以在 find_decoder* 里做手脚没用。

问题 2：RK3399 没有 HEVC 硬编，前端却要 HEVC
  [debug] codec_id 173, Rockchip MPP HEVC encoder
  [hevc_rkmpp] Failed to init MPP context: -1
  mpp: unable to create enc h265 for soc rk3399 unsupported
  => RK3399 的 VEPU2 只能编 H.264(+MJPEG)。浏览器（Edge 装了 HEVC 扩展）告诉飞牛前端
     "我能播 HEVC"，前端就发 "videoEncoder":"hevc"，mediasrv 拼出 hevc_rkmpp 去开 -> 必挂。
     跟源是不是 AV1 无关：任何需要转码的片子在这个浏览器上都会撞到。

解决：LD_PRELOAD 垫片 _work/rktools/mediasrv-shim.c（约 250 行，只用 libc+dl）
  - av_codec_iterate() 里把 av1_rkmpp / vp8_rkmpp 藏起来 -> mediasrv 自己走 libdav1d / libvpx
  - avcodec_find_encoder_by_name() 里把 *_rkmpp 且不是 h264_rkmpp/mjpeg_rkmpp 的
    一律改写成 h264_rkmpp（hevc_rkmpp/av1_rkmpp/vp9_rkmpp…）
  - avcodec_open2()/avcodec_find_decoder*() 只记日志到 /tmp/mediasrv-shim.log
  不能在 avcodec_open2 里偷换解码器：ffmpeg 8 会拒绝
  "This AVCodecContext was allocated for av1_rkmpp, but libdav1d passed to avcodec_open2()"，
  必须在分配上下文之前就让它选对，所以只能从 av_codec_iterate 下手。

安装（一条命令，脚本在 BOOT 分区也有一份，系统更新后重跑）：
  sudo am40-fix-mediasrv            # 装/重装（优先现场 gcc 重编）+ 重启 mediasrv
  sudo am40-fix-mediasrv --status   # 只看状态
  sudo am40-fix-mediasrv --remove   # 摘掉，恢复原样
文件：/usr/local/lib/mediasrv-shim.so、/etc/systemd/system/mediasrv.service.d/10-am40-shim.conf
      /usr/local/sbin/am40-fix-mediasrv、/boot/{am40-mediasrv-shim.c,.so,10-am40-shim.conf,am40-fix-mediasrv.sh}

实测（用户真实片源 /vol4/.../Hyouka 2012 S01E01-[1080p][BDRIP][AV1.OPUS].mkv，
      AV1 Main 10bit 1920x1080 23.976fps + Opus + ASS + MJPEG 封面）：
  请求 {"req":"media.getPlayLink",...,"videoEncoder":"hevc","subtitleIndex":2,1080p}
    修复前 {"result":"fail","errno":68157450}
    修复后 {"result":"succ","playLink":"/media/<hash>/preset.m3u8","hlsTime":4,...}
  垫片日志链条：
    find_encoder_by_name("hevc_rkmpp") -> 改用 "h264_rkmpp" -> h264_rkmpp
    iterate: 隐藏 vp8_rkmpp / av1_rkmpp

  分片 ffprobe：h264 High 1920x1080 + aac，字幕已烧进去。
  回归：H.265 1080p->720p 用 hevc_rkmpp 硬解 + h264_rkmpp 硬编 ✓
        H.264 1080p->720p 用 h264_rkmpp 硬解 + h264_rkmpp 硬编 ✓

⚠ 速度：AV1 转码只有 ~0.36x 实时。单测（6s 素材，ffmpeg -benchmark）：
    只软解 AV1 10bit 1080p = 1.63x（不是瓶颈）
    软解 + H.264 硬编      = 0.49x   ← 瓶颈是编码器（h264_rkmpp 只有 ~0.67x）
    mediasrv 全链路(+烧ASS+AAC+HLS+机械盘) ≈ 0.36x

  缓解：① 让飞牛先把整集转码缓存好再看；② 播放器里选 720p 档。
  想真正解决只能回头啃 MPP H.264 编码性能。

结论先放这：
  满编 MPP 模块（旧） vs 飞牛原版模块，跑在同一个 DTB、同一个 297MHz 下：
      1080p H.264 编码  0.66x  vs  1.25x
      1080p H.264 解码  1.37x  vs  3.33x
  差一倍，不是时钟、不是容量、不是 userspace 库，而是我这份内核模块
  每帧调用了一次 6.18 已废弃的 iommu_set_fault_handler()。

1) 先排除时钟（走了一段弯路，记录下来免得再走）
   /proc/mpp_service/vepu/aclk 可写（= mpp_clk_info.debug_rate_hz 覆盖），扫频：
      297MHz -> 0.66x | 400MHz -> 0.76x | 594MHz -> 0.89x | 800MHz -> 1.23x | 1000MHz+ -> 0.03x
   800MHz 能追平原版，但那是拿 2.7 倍功耗换回"本来就该有的速度"；
   1GHz 反而把编码器打到 1fps。**不要超频**，厂商默认 300MHz 是对的。
   （顺带确认：aclk_vcodec 空闲 50MHz/REDUCE、任务中 297MHz/NORMAL，驱动在管；
     编码时 CPU 只占 40%，不是 CPU bound。解码速度对时钟完全不敏感 1.36~1.37x。）

2) 真凶
   drivers/video/rockchip/mpp/mpp_iommu.c: mpp_iommu_dev_activate()
       iommu_set_fault_handler(info->domain, dev->fault_handler ?: mpp_iommu_handle, dev);
   6.18 起 domain->ops->set_fault_handler == NULL -> WARN_ON + 整页调用栈
   （含 1.5KB 的 "Modules linked in: ..."）。而"激活设备"是每帧一次：
          编码 300 帧 -> dmesg 287 条 WARN；解码 300 帧 -> 同样 287 条。
   fnEnv.txt 是 console=both，这些 WARN 同时刷串口(1.5Mbps)+HDMI 控制台，
   一帧的打印开销比编码本身还大 -> 吞吐直接砍半。
   不重编也能验证： sudo dmesg -n 1（只让 emergency 上控制台）
          编码 600 帧 0.66x -> 1.17x ；解码 1.37x -> 9.2x

3) 修法
   _work/rktools/am40-patch-iommu.py（板上 /boot/am40-patch-iommu.py）把那段调用 #if 0，
   并给 mpp_iommu_handle 加 __maybe_unused。6.18 的 rockchip-iommu 自己在中断里报
   page fault，不需要驱动再注册。重编后版本号 custom-rk3399-full-v3。
   （用户给的 mpp-develop 1.1.0 的 kmpp/ 里已经完全没有这套 fault handler，
     方向一致；但那是新一代对象模型，跟板上 librockchip_mpp(a9380ef) 不是一套接口，
     不能直接替换，所以只取"去掉这个调用"这一个结论。）
